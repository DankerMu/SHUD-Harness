# Design

## Issue #450 implementation boundary (including #490)

Change surface: new shud-first-task.sh and typed driver under scripts/runtime, package.json command; PI-approved minimal shared shud-web-driver.ts extraction and restart caller migration, script-only evidence helper if needed for a single auditable verdict implementation, knip root entry and pinned ws/@types/ws plus lockfile. No packages/host/instructions/constraints changes; #451 owns control-plane registration.
Governing invariant: exit0 means one real coordinator/worker first-task chain has identity-bound durable evidence and an actually allowed report_submit audit, not merely accepted-looking files or model claims; every spawned process is either safely quiesced by owned identity or explicitly reported as unsafe to clean, never blindly signalled.
Must preserve: existing shud-restart-evidence.ts five-assertion oracle, natural full ccw restart case timing/input and both SIGTERM/SIGKILL scenarios, delivered wake/completed-only indexes, bounded secret-safe subprocess/HTTP behavior, no host-source import and no generic retry. #490 changes only the restart session's explicit preset to worker; root owner_session remains the same root session. Freeze existing package tests and restart oracle before migration.
Extract shared code rather than copy WebHost/secret IO/owned command transport into a second shell implementation. Both drivers import the same typed helper; remove obsolete private copies, no shim/re-export. Keep restart-only process sampling/evidence/preflight local. Shared parameters are only real differences (interaction mode, optional one-off patch before app args, root/subagent session addressing); preserve identity checks, bounded output/drain, stateDir ownership and cleanup. Reuse existing public process-group/identity capabilities; never import host internals.
The shell requires one explicit scratch workspace argument, optional --patch <file> solely to exercise ordinary disposable overlays, no other modes. Before any profile/host/session: require nonblank DMXAPI_KEY, explicit absolute executable ordinary SHUD_BIN (no restart fallback), pinned dsh via existing resolver, valid optional overlay and copied-source ccw availability. Missing argument/tool/key must fail nonzero with its name. Do not inspect TMPDIR location or reject a scratch path because it is temporary.
Resolve the workspace physically; create it if absent, reject unsafe links/non-directory managed input targets and never overwrite preexisting unrelated input/records. Copy the read-only SHUD/input/ccw into a new owned input/ccw using the existing copy/hash convention; refuse an existing destination instead of silently replacing it. Keep source input hashes unchanged and compare retained copy. Create a fresh independent DSH_HOME for every invocation, not the caller's existing profile. Retain workspace/home/session evidence on success and failure; never delete supplied workspace or arbitrary runs.
Build and install the actual Web profile, then drive one user prompt describing task_create→explicit worker with task_id/input_dir→ccw end_days30→job_output(dsh_job_id,wait:true)→worker shud_collect(persistent id)→return→report_generate/report_validate/report_submit. No second steering/repair prompt, no fake tools or direct script-generated TaskCard/report; model deviations fail this run. Legitimate model report regeneration after failed validation may occur; anchor acceptance on the submitted report, not the first generated id.
Explicit worker selection follows the delivered preset subtree: the effective installed coordinator tool-subagent configuration selects provider spawn and agentPreset worker; the actual catalog/child header must confirm the resulting worker. It does not require a model-supplied agent_preset argument: the pinned host rejects that argument when allowedAgentPresets is absent. Independently capture the effective configured binding for the live verdict, reject missing/foreign bindings, and retain separate negative controls; do not change the profile or invent model-selectable presets to satisfy a synthetic fixture.
Approval uses loopback /connect with interactions=answer, a bounded ws client stream /api/remote.mux $events and HTTP $events/result. Explicit ws dependency avoids hidden host-layout require and homemade framing. Answer allowed-once only for a report_submit invocation owned by this coordinator, matching a validated report id/call and the actual request; decline/delegate unexpected approvals, never blanket-allow raw/scientific changes. Track client/event identity, process each invocation once, close stream/listeners during cleanup. Tokens/cookie/key stay in memory and are screened from all saved diagnostics/results.
The approval loop is passive: absence of approval must not keep the run waiting forever. Completion is a terminal submitted result or bounded failed chain/turn, not receipt of an approval card. The policy-disabled overlay can yield accepted JSON/Markdown/done TaskCard without any ask; it MUST reach verdict evaluation and fail the missing joined approval predicate, rather than pass files-only or merely time out waiting for a nonexistent card.
Use canonical session evidence, not transport callbacks as the oracle: coordinator tool call/result ids, subagent/catalog child id and header parent/origin/preset, worker call/result sequence, worker collected RunRecord before completion, coordinator subagent-settled source tied to that child before report generation, successful validate of the submitted id, submit asked.callId→asked.id→decided.id allowed-once→same-call successful tool result. Sequence numbers are comparable only within a session; cross-session links use actual parent/child/catalog/settled identities and persisted timestamps only where their semantics permit.
Read root and worker through appropriate public session addresses or canonical stored logs after positive flush. Child ids may be bare UUIDs; do not reuse restart's session-prefixed-id assertion for them. Prove stored evidence with explicit export/flush and canonical log paths; a live WebSocket frame alone is not durable audit evidence. Reject duplicate/mismatched result identities, failed collection, foreign run/task/report/decision or approval of another report.
File oracle parses core TaskCard/RunJob/RunRecord/EvidenceReport/StackLock/DataProvenance schemas and verifies identity joins: done task links submitted report and worker run/job, collected job and succeeded/exit0 RunRecord, same task/stack/data, report accepted decision with exact submit callId approval_ref and accepted/null comment. Canonical Markdown must match fresh deterministic render (safe references), contain accepted watermark and literal governance invariants; referenced StackLock llm base_url/request_alias/response_model and all three actual repository revisions appear in the report. No newly invented scientific or numeric-quality claims; missing model response metadata is a failure, not fabricated.
Evidence summary exposes named PASS/FAIL predicates, ids and file/session paths, not credentials or unbounded model text. On failure print retained workspace, home and any known coordinator/worker canonical session paths; before session creation say no session started and retain only paths actually created. Error diagnostics name controlled stage/predicate, never arbitrary raw request/cause payload.
Cleanup stops/awaits host(s) and stream/output handles; for detached SHUD work use only current owned run identity, command/workspace/owner_session/wrapper proof and recoverProcessGroup. Unknown/lost/reused identity or unverifiable historical descendants means retain evidence and fail explicitly, not success cleanup or bare PID/PGID signal. The child owner is worker, not coordinator. Cleanup must still discover owned durable submission if a tool result was lost; do not require successful report evidence before draining resources.
Required evidence: new CLI/oracle fails against absence/prechange; real TMPDIR ccw30 happy path with all audit/files and source hashes; same actual chain with disabled-policy overlay fails specifically missing approval even when accepted files exist; missing workspace/key/bin/host before session, invalid/occupied input no overwrite; fault snapshots of missing/foreign/reordered worker collect, validation/report/approval joins, watermark/stack/invariant mutations reject. Exercise timeout/interruption/HTTP/WS loss cleanup with owned scratch, no LLM retry loop. Real migrated shud:restart SIGTERM and SIGKILL cases retain all five old assertions and delivered wake.
Review refinements preserve this evidence floor: reject malformed overlay syntax/shape before side effects; each report generation needs a same-child settled notice strictly after the delegation result. Approval close drains resources and propagates late protocol/processing failure. Shared managed-file reads open no-follow/nonblocking, validate regular descriptors, cap bytes and always close; wrapper ownership reads use the same primitive. Enforce single-worker/single-run cardinality before repeated log/group ingestion and bound failure discovery without claiming unknown work was cleaned. RPC body reads explicitly own abort/deadline cancellation through reader cleanup rather than relying solely on fetch propagation. Add native special-file, close-only late-fault, preterminal fanout, byte-boundary, HTTP stall and post-admission interruption controls; withholding the driver's child-export response proves non-observation, not absence of a worker-persisted result.
Verification boundaries: first-task.sh is a local engineering gate, not PI functional acceptance; optional overlay does not make disabled policy a supported production profile. No report_decide/reject path here. Default check/strict/profile plus actual first-task positive/negative and restart gates precede merge; three seats focus correctness, test-evidence/spec and security/invariant lifecycle. All modules stay ≤1000 lines and existing coverage/duplication/import gates unchanged.

Must preserve: #446 independent reconcile/entry repair and JSON→card→Markdown commits, readonly reference IO, default collection, canonical applyDecision/transitionTask/rendering, older-report repair precedence, controlled errors and all nonterminal tool contracts.

Both tools use strict-tool. submit accepts exactly report_id; decide exactly report_id/disposition/comment, disposition required rejected|revision_requested, comment a nonempty string per canonical schema (preserve whitespace/newlines verbatim, no trim/default/reinterpretation). Invalid roots/keys/brands/comment/disposition fail without domain writes. Result is structured report_id/status/decision_id. Only fields owned by existing pure transitions change; preserve report evidence/prose/created_at and unowned fresh task fields/links. After report JSON commit, task_card/render failures include report_id, preserve prior commits, and do not rollback/retry. A later report-id call repairs the already durable decision before rejecting its wrong precondition, never creates a second decision.
Normal approved step-2 projection is an explicit decision transition, distinct from older-report entry repair. Do not add an unstated latest-report-only approval restriction or re-run closure/validator at submit: the specified precondition is reviewed. Already-terminal repeated calls cannot change history, status or comments.

Use one small tools-local per-report promise lane, no service/config/timer/persistent lock/retry. Approval happens before entering the lane, so a waiting PI card never holds it. Fresh reads and preconditions occur inside; independent reports advance independently, errors release the lane, completed tails are removed.

Generation still obtains closure before new JSON, then immediately registers that id's card/Markdown publication without an intervening yield; all card transforms remain synchronous. Physical cwd aliases must address the same lane. This is single-process tool ordering, not cross-process filesystem transaction or protection against external namespace replacement.
Required concurrency input: two approved same-report decisions with missing/stale Markdown and a held asynchronous write; exactly one terminal history entry wins, the other sees fresh terminal state, final Markdown equals canonical rendering of durable JSON. Also hold validation/entry repair or generation publication before an approved terminal call; no late draft watermark regression. Different-report control must progress while one lane is held; failed operation must not strand later repair.
Raw guard sends both new names to the existing report-id exact JSON/Markdown/task-target path. Protected write targets deny before policy ask/execute, even when approval would allow; malformed ids never become paths. Preserve unrelated-target controls and #446 non-creating missing-reference behavior. No new parser or blanket report-tree rejection for known ids.

ADR-0011: status proposed, kind architecture or process per decision content, #426/O5 and PI comments are provenance, not a claim this new ADR was separately PI-accepted. Explain native card outcome versus domain outcome, comment via dialogue plus full second-card confirmation, no default disposition, exact callId→asked.id→decided.id audit, alternatives (new form seam/PI-only tool) and limits. CONTEXT companion points to actual terminal-tool integration tests, not fake-tool policy tests or nonexistent future files.
Allowed old-test migration: remove only #446's now-obsolete assertions that terminal tools are unmounted from report-raw-guard.test.ts, preserving its disjoint generation assertions; replace with actual new tool registration/authorization tests. No weakening of old report/collector/raw/renderer/state oracles; do not rewrite historical fixture evidence.

Parent authorizes adding only writeReport(h.cwd) before that call; every existing denial/approval-count/role assertion remains unchanged. This is a resolvable-target fixture correction under the new raw contract, not a policy production change or weakened oracle. Together with the obsolete unmounted assertion removal, all other prior test files remain byte-identical.
Sibling surfaces: both terminal tools, report_generate/report_validate shared repair/publication, records applyDecision/task transitions/non-creating renderer, raw exact targets, policy serviceAsk/reason/displayReason/caller role, core decision brands and CONTEXT/ADR.
Parent evidence: tests-only RED including semantic raw admission/publication controls, full default gate/strict/ADR/profile/raw T1–T5; independent built real ccw→collect→generate→validate then accepted/rejected/revision paths through real ToolRuntime+mounted policy and approval doubles, file/history/watermark/raw snapshots and callId assertions. Doubled approval service does not prove session-log persistence, actual Web cards or PI acceptance; these remain #450/#452.
Review focus: only allowed execution writes, exact audit identity/comment, no terminal overwrite or late Markdown regression, independent repair/partial commit retention, raw-before-ask and old consumer compatibility.

## Issue #446 implementation boundary

PI decisions: issuecomment6522484479 supersedes the original tools-only boundary and contradictory ordering/no-write clauses before implementation. Only task 6.2 is selected.
Change surface: two tools and shared local report workflow helpers; minimal records non-creating reads/safe Markdown IO; a registry-owned read-only collection-attempts accessor using the existing ledger parser; raw-guard admission and necessary existing-workspace dependency wiring. No core schema, collector algorithm, renderer/validator/state-machine rewrite or host changes.
Governing invariant: only closure-eligible evidence produces a new draft; report JSON is authoritative, each accepted repair is independent, and no error or recovery bypasses raw protection, identity binding or legal TaskCard transitions.
Must preserve: all old tool contracts, records readWorkspaceRecord directory-creation behavior for existing callers, M2 collector/cached-record/retry behavior, query admission/drain, pure report mapping/predicate semantics, rendering bytes, thirteen validation checks, wording/secret boundaries and report terminal approval exclusivity.

Generate order: strict arguments/TaskId/session cwd → non-creating schema-valid identity-bound TaskCard read and allowed-state check → resolve every authored citation without writes → listRunJobsByTask → fresh synchronous card identity/state check, canonical reconcile and publish only if changed → evidence reads → fresh card/closure validation → new draft JSON → fresh synchronous card transition/link append → render and safe atomic Markdown publication.
Allowed generate states are planned/running/reporting. Successful reconcile is independent; any later failure retains it. No-op reconcile preserves bytes/mtime. Invalid state or citation never creates directories, calls collect, or changes cards/reports. Unknown/malformed/foreign objects fail closed.
Only already-collected jobs are passed to collectShud(id, {readonly:true}) to retrieve canonical RunRecords; uncollected jobs remain closure failures, not implicit collection work. PI issuecomment6523542892 authorizes this explicit mode because default collection can journal corrupt cached records or generate missing ones. Default collectShud calls remain unchanged; readonly mode shares owned indexing, canonical existing-record parsing and the existing per-entry admission/queue/drain, but bypasses generation, failure accounting, projection, receipt completion and notification. Missing/corrupt/unsafe/wrong-identity evidence fails without any file mutation. No duplicate parser or preflight-plus-mutating-call workaround.
Read retained collect-error attempts separately even when a valid cached RunRecord exists; missing ledger means zero, invalid/unsafe/unreadable ledger is a controlled error, and attempts at/above MAX still block after successful direct collection. Never duplicate parsing or erase/reset the ledger. The readonly collection mode itself remains a canonical record retrieval, not a replacement for the closure attempt check.
The new jobs accessor accepts a branded persistent run/job id, resolves the owned active-before-completed index, validates current run path/identity, reuses the canonical strict ledger reader and returns attempts only. It has ready/closed admission and drains accepted reads before unlock using existing query lifetime tracking. No polling, collection, persistence, discovery, retry or raw ledger-text disclosure.
Citation tokens are the six specified PREFIX-YYYYMMDDTHHMMSS-xxxx forms with token boundaries, subsequently validated by the core brand schema. TASK/STACK/DATA/REPORT require a safe existing schema-valid file with matching embedded id; RUN/JOB require an owned index entry. Deduplicate lookups; DEC and malformed/non-token substrings do not invent a new citation grammar. Inspect all four authored fields, not automatic limitations.
After asynchronous evidence reads, reread the card before committing the report and evaluate closure against its fresh linked_jobs. ## Decisions

### D1 三个新包与职责边界

- `@shud-harness/dsh-shud-records`（运行时无 Cordis 依赖的文件层）：四对象的工作区文件读写、原子写入、品牌 id 分配、StackLock/DataProvenance 确定性采集、EvidenceReport 模板填充/水印/validator/状态机、TaskCard 状态机与 closure 谓词的持久化绑定。只依赖 `dsh-shud-core` 与 Node 内置模块。
- `@shud-harness/dsh-shud-policy-gate`（Cordis 插件）：第二个 `tools/pre-execute` 监听。
- `@shud-harness/dsh-shud-presets`（Cordis 插件 + bundle patch 片段）：两个 preset 行与全局 `shud-role-restrict` 生命周期插件。
- 模型工具（`task_create`、`report_generate`、`report_validate`、`report_submit`、`report_decide`）放在现有 `dsh-shud-tools`，复用其 strict-tool 适配；`dsh-shud-jobs` 在提交时经 records 解析/采集 lock 与 provenance。依赖方向：core ← records ← jobs ← tools；policy-gate、presets 只依赖 core（+ records 读报告状态）。

备选：把对象持久化并入 jobs（jobs 已 >10K 行且是 Critical Path #4，混入报告逻辑扩大白盒审查面）；并入 tools（tools 是工具契约层，records 要被 jobs 消费会倒置依赖）。均否决。

### D2 工作区文件落点与原子写

```
<session cwd>/
  tasks/<task_id>/task.json
  stacks/<stack_id>.json
  provenance/<data_id>.json
  reports/<report_id>.json          # EvidenceReport 对象（含 decision_history）
  reports/<report_id>.md            # 由 .json 确定性渲染；每次状态变化重渲染
  runs/<run_id>/…                   # M2 不变
```

原子写 = 同目录临时文件 + `rename`，复用 `dsh-shud-jobs/src/state-files.ts` 的实现：该实现**移入 records** 并由 jobs 改为 import（Canonicality，原地重构）。唯一例外是 StackLock 文件：以 `wx`（排他创建）写入，`EEXIST` 时重新生成 `stack_id`，至多 3 次，仍冲突则报错（lock 只新建、从不改写，排他创建即是其原子性）。读取经 core schema 校验，损坏文件 fail-closed 报错、不改写。不建索引：查找按 id 直接定位文件；"当前 lock" 由 D5 定义，不需要"最新"查询。

路径安全（规范要求落在 `specs/task-cards` 的 "TaskCard workspace file"，其余对象 spec 以一句引用）：

- id 在任何路径拼接之前先经品牌 schema 校验；工具与 policy-gate 插件从不由原始字符串构造路径，只由品牌 id 构造。
- `<cwd>/tasks`、`stacks`、`provenance`、`reports` 不存在时 `mkdir -p` 创建；已存在时先 `lstat`，凡不是真实目录（符号链接、普通文件等）一律 fail-closed。
- 目标文件在读写前 `lstat`，符号链接与特殊文件 fail-closed；写入为同目录临时文件 + `rename`（StackLock 按上文 `wx`）。

备选 `ctx.storage`（PI 不可直接读，且 M2 D2 已否决）；stateDir 索引（M3 无并发/跨工作区查找需求，YAGNI）。

### D3 品牌 id 与 schema 对齐（Critical Path #7）

- `run-identifiers.ts` 的生成器泛化为 `createBrandedId(prefix)`，格式 `<PREFIX>-YYYYMMDDTHHMMSS-xxxx`（UTC 秒，4 位小写 hex），新增 `TaskId`、`StackId`、`DataId`、`ReportId`、`DecisionId`（`DEC-`）品牌类型；schema 拒绝旧格式（`TASK-0001`、`DATA-<UUID>`）。同一 TaskCard 创建的对象不共享随机段（与 JOB/RUN 配对规则不同，那是同一作业的两个视角）。冲突（同秒同随机段已有文件）重新生成。
- `TaskCardSchema`：`task_id: TaskId`；`stack_id`/`data_id` 为 `StackId | null` / `DataId | null`（M3 由 `shud_run` 回填，建卡时 null）；`linked_jobs: JobRecordId[]`、`linked_reports: ReportId[]`；`reviewer` 保留；`theory_bundle_ids` 保留 optional。`type` 枚举不变。
- `StackLockSchema`：`llm` 收窄为 `{ base_url, request_alias, response_model }` 三个非空字符串；`repos.<name>` 增加 `dirty_paths: string[]`（排序后的 POSIX 相对路径，来自 `git status --porcelain` 第二列，`dirty === dirty_paths.length > 0`，但溢出判 dirty 时 `dirty_paths` 可能不完整——记录 `dirty_paths_truncated: boolean`）；`runtime` 改为 `{ os: string, sundials_version: string | null, host_version: string }`（`host_version` 为钉版 dsh 版本，来自 `shud-jobs` 行配置 `hostVersion`），删除 `r_version/r_packages_lock/python_version/gcc_version/gdal_version`（nullable 也不保留：无采集者的字段是假数据）；`harness` 改为 `{ version: string }`（本仓库 `package.json` version），删除 `cli_version/prompt_pack/skills_version`。`computeStackFingerprint` 排除集加入 `llm.response_model`（K4）。
- `DataProvenanceSchema`：`data_id: DataId`；`sources` 改为 `{ input_root: string, files: [{ path, sha256, size_bytes }] }`（排序 POSIX 相对路径，覆盖输入目录副本全部普通文件）；`basin: string`（= project）；`event_window: { start: string | null, end: string | null }`（M3 为 null，见 Not yet specified）；`preprocess`、`uncertainty_notes` 为 `null`。原 `terrain/mesh/forcing/observations` 分类删除（无采集者）。
- 新增 `EvidenceReportSchema`：`report_id`、`task_id`、`status`（7 态）、`summary`、`observations[]`、`limitations[]`、`pi_questions[]`（非空字符串数组）、`linked_runs: RunId[]`（非空）、`stack_ids: StackId[]`、`data_ids: DataId[]`（非空、去重，生成时从每个 linked RunRecord 解析；多运行可含多个 lock）、`llm_response_models: string[]`（来自 linked RunRecord，去重非空）、`decision_history: PiGateDecision[]`、`created_at`、`updated_at`。
- 新增严格 PiGateDecisionSchema，字段恰为 decision_id（DecisionId）、report_id、approval_ref（本次工具调用的 callId，非空；经日志 approval/asked.callId 关联审批 id）、outcome（accepted/rejected/revision_requested）、comment（accepted 仅 null，其余非空）、decided_at。O5 实测工具上下文没有 approval id；不新增日志订阅取 id 的第二路径，不记录先前被拒 submit 卡引用。
- `Minimal_Schemas.md` 对应段按本 D3 逐项写处置，其中既有 `PiGateDecision` 段（原字段 `decision_id, gate_id, task_id, actor_user_id, actor_role, decision, comment?, comment_required, next_action?, evidence_refs, created_at` 与 A01-2 映射）被**改写**为本条 M3 schema，不另增一段：只保留 `decision_id`，`decision`→`outcome`、`created_at`→`decided_at`、`comment?`→必填且仅 `accepted` 为 null，其余字段删除；权威源 `Support_Schema_Contracts.md` §6 同刀改写（连同 `idempotency_key`），投影声明不变；`pnpm run schema:generate` 刷新投影；`CONTEXT.md` 第 2 条"代码在 M3 前仍带旧字段"解除。

备选：保留 StackLock 全量 runtime/harness 字段设 nullable——否决（没有采集者的字段是假数据，违反"无 placeholder"；PI 于 2026-10-27 Stage 3 确认删除）。备选：PiGateDecision 记录被拒 `report_submit` 卡的引用并由 `report_decide` 参数传入——否决（PI 2026-10-27：审批 id 仅 log 可见，模型无来源）。

### D4 TaskCard 状态机与 closure 谓词

转换表（records 纯函数 `transitionTask(card, event)`，非法转换抛错，不改文件）：

| 事件（来源） | 前态 | 后态 | runtime_phase |
|---|---|---|---|
| `task_create` | — | `planned` | null |
| `shud_run(task_id)` 提交成功 | `planned`/`running` | `running` | `submitted_job` |
| reconcile 发现非终态的链接作业 | `planned` | `running` | `submitted_job` |
| `report_generate` 且 closure 谓词成立 | `running`/`planned`/`reporting` | `reporting` | null |
| `report_submit` 获 `allowed-once` 执行 | `reporting` | `done` | null |
| `report_decide(revision_requested)` 获 `allowed-once` 执行 | `reporting` | `planned` | null |
| `report_decide(rejected)` 获 `allowed-once` 执行 | `reporting` | `cancelled` | null |

非法转换示例：`planned` 且 `linked_jobs: []` 时 `report_generate` → closure 错误（无作业），文件不变；`done` 时 `report_decide` → 错误，文件不变。

报告重新生成：每次 `report_generate` 分配新 `report_id`，写新的 `reports/<report_id>.{json,md}` 并追加到 `linked_reports`；先前报告文件原样保留（字节与 mtime 不变）。`report_validate` 失败的 `draft` 报告保持 `draft`，coordinator 修正输入后再调 `report_generate`（新 id），或就此搁置；`report_validate`/`report_submit` 只作用于传入的 `report_id`，只有 `reviewed` 报告可提交。`revision_requested → planned` 之后：PI 要求重跑则 `shud_run(task_id)`（`planned → running`）；不要求重跑则直接从 `planned` 调 `report_generate`（既有已收集运行仍满足 closure 谓词）。新旧报告的延续关系见 Not yet specified。

`awaiting_pi`（TaskCard 与 EvidenceReport 的枚举值均保留）在 M3 是审批卡挂起期间的瞬时态：dsh 的 `ask` 在工具执行**之前**决定结果，放行即执行、拒绝即不执行，没有可落盘的中间时刻，因此 M3 不写入 `awaiting_pi`，TaskCard 停在 `reporting`、报告停在 `reviewed` 直到某张卡放行。

`created` 只在建卡原子写入前的内存态；`parked`/`blocked` 在 M3 无进入转换（Non-Goal）。`updated_at` 每次转换刷新；`linked_jobs` 在 `shud_run` 提交时追加，`linked_reports` 在 `report_generate` 时追加。

`shud_run(task_id)` 的回写顺序（#445 PI 澄清，issuecomment6519965712）：(1) 品牌 id 校验 → 取得关联作业 → 同步读取并校验 TaskCard 身份与 `planned|running`，不可运行卡直接拒绝、不发布 reconcile；可运行卡再 reconcile（见下）并仅在变化时原子写回 → (2) M2 提交（durable；RunJob 携带 `task_id`、`stack_id`、`data_id`）→ (3) TaskCard 读取—校验—转换—`writeJsonSync`，读与写之间不 await（沿 M2 RunJob 同步边界规则）。初始对账是独立提交点，后续新提交失败不撤销旧作业修复；第 3 步失败返回工具错误，指明 `run_id` 与"运行已 durable、任务卡回写失败"，运行不回滚。

TaskCard reconcile（唯一一条卡↔作业对账规则，`specs/task-cards`，records 4.3 拥有）：`reconcileTaskCard(card, runJobsForTask)` 令 `linked_jobs := union(card.linked_jobs, task_id === card.task_id 的 RunJob)` 并按码点升序排序；以其中最新 RunJob（`submitted_at` 最大，相同时取 `job_id` 码点序最大者）填补为 null 的 `stack_id`/`data_id`，从不覆写已非 null 的值；卡为 `planned` 且任一链接作业未终态时按转换表置 `status: running`（`runtime_phase: submitted_job`）；没有任何变化时不写文件。它在 `shud_run(task_id)` 与 `report_generate` 开头调用。注册表查询 `listRunJobsByTask(task_id)`（活动 + 完成索引，按 `job_id` 码点升序）由独立切片 5.2 拥有（只读 API，不依赖 5.1 的提交事务）：任一已索引条目的路径/身份校验失败、`run-job.json` 不可读或未通过 schema 时以指出该 `run_id` 的错误 fail-closed 拒绝，不跳过该条目；与 `collectShud` 相同，就绪之前与关闭准入之后拒绝。并发：单进程、同步边界，不会交错。

closure 谓词（`science_assist`）在 `report_generate` 内、reconcile 之后求值，全部成立才通过：`linked_jobs` 非空；所有 `linked_jobs` 的 RunJob 处于 `collected`（有 RunRecord）；每个 RunRecord 的 `stack_id`/`data_id` 非 null；待写入的报告 `observations/limitations/pi_questions` 各 ≥1；每个 metric_fact 有 evidence_refs——M3 报告没有 metric_fact（Non-Goal），该子句恒真并在报告 limitations 自动追加一条"无指标 artifact"。链接的 RunJob 处于 `failed`/`cancelled`（已收集者即 RunRecord `status: failed`，含取消/丢失的 `exit_class`），或收集已耗尽（存在 `collect-error.json` 且 `attempts ≥ MAX_COLLECT_ATTEMPTS`）时，closure 不成立，错误子句点名该作业；卡保持 `running`——M3 没有 TaskCard 取消工具，PI 可对仍在运行的作业 `job_kill` 或保留该卡。谓词不满足时工具返回错误、不写报告、不改状态。LLM closure 分类器不实现（advisory，M3 无消费者）。`engineering`/`ops` 的建卡在 M3 被 `task_create` 拒绝（schema 枚举保留，工具参数 `type` 必填且只接受 `science_assist`），避免产生永不可关闭的卡。`task_create` 其余字段确定性填充：`created_by` 与 `current_owner` = 调用 agent 的 preset id（`coordinator`，读取路径见 D10，可读性由 O6 核实），`reviewer` = 常量 `pi`，`inference_budget` = `{ mode: "normal" }`，`linked_jobs/linked_reports` 空数组，`stack_id/data_id` null（由 `shud_run` 回填）。closure 谓词在 `linked_jobs` 为空时不成立；"limitations ≥1" 按模型传入的条目计数，自动追加的"无指标 artifact"一条不计入。

### D5 StackLock 采集与"当前 lock"

`shud_run` 提交时（输入复制完成、RunJob 写入前）由注册表调用 records 的 `captureStackLock(config, llm)`：

- 采集配置全部挂在既有 `shud-jobs` 行（records 包不是 Cordis 插件，没有自己的行）：`Config` 并集扩展为 `LocalJobRegistry.Config ∪ {stateDir, shudBin, stackRepos.{SHUD,rSHUD,AutoSHUD}, sundialsRoot?, hostVersion, llm.base_url, llm.request_alias}`，缺失即 apply 失败（fail-loud）。`profile:install` 与写 `shudBin` 同一机制写入这些键：`stackRepos` 从本仓库根派生绝对路径（三目录须存在），`hostVersion` 取 bundle 钉版 `@deepseek-ai/dsh` 版本，`llm.*` 取 bundle patch `llm-deepseek` 行的 `baseURL` 与 `agent-default-model` 的 `model`；`sundialsRoot` 取环境变量 `SUNDIALS_ROOT`（设置时须为存在目录），未设置则不写该键（采集为 null）。安装器整体拥有该 patch 项，重装以当次环境为准。
- `repos`：对 `stackRepos.*` 调用 `collectRepositoryRevision` 并扩展返回 `dirty_paths`：既有 `git status --porcelain` 调用改为 `--porcelain -z`（NUL 分隔、无引号转义，`core.quotePath` 不影响），每条记录取路径字段，重命名/复制条目（`R`/`C`）只记新路径，去重后按码点升序排序；溢出判 dirty 时 `dirty_paths_truncated: true`。不新增 git 调用。
- `runtime.os` = `os.type() + " " + os.release()`；`runtime.sundials_version` = 读 `sundialsRoot`（可选）下 `include/sundials/sundials_config.h` 的 `SUNDIALS_VERSION`，无配置或文件缺失为 `null`；`runtime.host_version` = `hostVersion`。
- `harness.version` = 本仓库根 `package.json` version（构建期常量）。
- `llm.base_url`、`llm.request_alias` = `shud-jobs` 行的 `llm.*`（`profile:smoke` 断言与 `llm-deepseek` 行及 `agent-default-model` 一致）；`llm.response_model` = 本次 `shud_run` 的 configured 别名（与 RunJob 同源，`response_model_source` 不进 StackLock——它在 RunRecord）。
- 指纹按 D3 排除集计算。**当前 lock** = `stacks/` 下指纹相等的已有文件（多份时取 `stack_id` 码点序最小者，不改写）；没有则以 `wx` 写新文件（D2，`EEXIST` 重新生成 id，至多 3 次）。因此同一环境反复提交不产生新 lock，环境一变自然换 lock，无需"最新"概念。两个提交并发首次写出指纹相同的两份 lock 是允许的重复（两份都有效，后续复用取最小者）；提交回滚不删除任何 lock 文件（新写的 lock 可能已被并发提交复用，且它只是环境记录），只删除本次 provenance。
- 采集失败（任一 repo 不是仓库、配置缺失）→ `shud_run` 返回工具错误、不提交。

备选：独立 `stack_lock` 工具先调再跑（多一次模型调用，错漏面大）；报告时补采（与运行时状态脱节）。均否决（grill Q17）。

### D6 DataProvenance 生成

同样在提交时由注册表生成：对运行目录内 `input/<project>/` 副本（M2 已完整复制且已拒绝链接/特殊文件）遍历普通文件，计算 sha256 与大小，排序写 `provenance/<data_id>.json`；`basin = project`，`event_window` 两端 `null`，`input_root` 为原始 `input_dir` 绝对路径。每次提交一份新 provenance（输入副本是本次运行的事实；去重按内容指纹不在 M3 范围）；provenance 先于 `run-job.json` 原子写入，提交回滚时删除（lock 不删，见 D5）。RunJob 的 `data_id`、`stack_id`、`task_id`（来自工具参数，可缺省为 null）在同一次原子写入 `run-job.json` 时落盘；RunRecord 继承。raw 下的输入仍由 raw-guard 弹读审批卡（M2 D8 不变）。

### D7 EvidenceReport 生成、模板与水印

`report_generate(task_id, summary, observations[], limitations[], pi_questions[])`：

1. 无副作用读取并校验 TaskCard 身份与 `planned|running|reporting`；先校验 authored 字段中的六类品牌引用存在性，不创建缺失目录，失败不改卡片、不自动重试（PI issuecomment6522484479）。
2. 查询关联 RunJob，在新鲜同步卡片边界执行 D4 reconcile，成功回写独立提交；仅对已 collected 作业经 collectShud 读取 RunRecord，另经 jobs 规范只读入口读取保留的 collect-error 次数。异步读取后重新读取卡片并求 closure，不能丢掉新链接或隐式 collect 未收集作业。
3. 事实表由对象确定性生成：StackLock 三仓库 commit/branch/dirty（dirty 时列 `dirty_paths`）、llm 三字段、每个 RunRecord 的 `exit_code/exit_class/status/wall_seconds/response_model(+source)`、产物清单条数与总字节、stdout/stderr 路径（只记路径）。
4. 渲染 10 节模板（`packages/dsh-shud-records/templates/evidence_report.md`，构建产物随包；`Repository_Layout` 的根 `templates/` 规划改指向此处）：§5"指标与图表"固定写"本里程碑无指标 artifact，见 limitations"；§7 列出 `status != succeeded` 的运行（closure 已排除失败/取消运行，M3 中该节渲染为空列表，渲染器与 validator 仍覆盖）；§10 附 argv、日志路径、产物清单；limitations/治理节逐字渲染 `GOVERNANCE_INVARIANTS` 四句（D8）。
5. closure 谓词通过后才写 `reports/<id>.json`（`status: draft`）；随后 TaskCard → `reporting`、`linked_reports` 追加；最后渲染 `.md`。多运行时事实表逐 run 列出各自的 `stack_id`/`data_id`/`response_model`，不定义比较规则（Not yet specified）。

报告工具的提交点（`report_generate`/`report_validate`/`report_submit`/`report_decide` 共用）：报告 `.json`（提交点：`status`/`decision_history`）→ TaskCard 转换（同步边界）→ `.md` 渲染。提交点之后的失败返回工具错误，指明失败步骤与 `report_id`，不回滚任何已写内容。修复只有两种，且只在下一次针对该 `report_id` 的报告工具调用（四者任一）开头进行：(a) 卡尚未取得报告状态所蕴含的转换则先补做该转换——"尚未取得"定义为该 `report_id` 不在 `linked_reports` 中，或它是 `linked_reports` 的最后一项且卡状态与报告状态不符；较早的报告从不改变卡；(b) `.md` 过期定义为标题下的水印行与报告状态不符（`draft` 与 `reviewed` 共用同一水印），此时重渲染。这是报告工具仅有的对账行为；卡↔作业对账属 D4 reconcile。

PI issuecomment6522484479 澄清：入口修复先于本次工具前置条件与 validator，已成功修复独立提交，后续失败的“不变”以修复后为基准。修复必须通过既有合法 TaskCard 转换，非法转换返回 task_card/report_id 且不改卡片或继续 Markdown 修复；不能因旧未链接报告重开 done/cancelled。未链接的终态报告在内存完成所需合法转换后一次发布映射终态，不发布中间 reporting；不新增决定。awaiting_pi/archived 的工具侧修复在写前拒绝。report_generate 无 report_id，因此不发现/修复旧报告。

`.md` 的渲染输入 = 报告 `.json` + 其引用的 StackLock、DataProvenance、RunRecord 文件；每次重渲染重新读取它们；任一引用文件缺失 → 渲染错误，报告 `.json` 不变。

报告状态在 M3 的实际落盘序列：`draft` →（`report_validate`）`reviewed` →（`report_submit` 放行）`accepted`，或（`report_decide` 放行）`rejected`/`revision_requested`；`awaiting_pi` 不落盘（见 D4）。水印 `accepted` 首部行为 `Accepted by PI · <decided_at> · <decision_id>`（`Report_Generation_Spec` 的 `decision_at` 在 2.1 对齐为 `decided_at`）。

水印按 7 态表（`Report_Generation_Spec` §7.1）渲染为标题下第一行与文末最后一行；`accepted` 为首部 `Accepted by PI · <decided_at> · <decision_id>`；`archived` 继承归档前终态另加 `ARCHIVED`（M3 无归档转换，但渲染器与测试覆盖 7 态）。`.md` 不内联日志/产物内容、不含密钥（事实表只取 RunRecord 已脱敏字段）。

备选：插件内再调 LLM 写叙事——无 seam，且与"coordinator 即叙事作者"重复。否决。

### D8 语言护栏与确定性 validator

- `core/governance/wording.ts`：导出 `FORBIDDEN_REPORT_PHRASES`（§5 五条 + §5.1 五条，中文原文，共 10 条）、`GOVERNANCE_INVARIANTS`（四句固定文案常量：①单流域/单事件指标提升不等于模型改进；②校准结果不等于结构验证；③不得宣称模型机制已验证；④不得宣称普遍改进）与密钥形态正则常量 `REPORT_SECRET_PATTERN = /\bsk-[A-Za-z0-9_-]{8,}/`，测试钉正反例；报告模板在 limitations/治理节逐字渲染四句不变式；`constraints.yaml` review_only 的"措辞规则"条目转为 matrix（`pnpm run test`）。无 profile 覆写（放宽需 ADR）。
- `report_validate(report_id)`：draft → reviewed 的唯一入口，逐项执行 13 项 (D)：(1) `stack_ids` 各解析到 StackLock 文件且 `stack_id` 一致；(2) `data_ids` 各解析到 DataProvenance 文件；(3) 每个 `linked_runs` 有 RunRecord；(4) 指标来自确定性 artifact；(5) limitations 非空；(6) pi_questions 非空；(7) 禁止用语扫描模型撰写的 `summary/observations/limitations/pi_questions`（子串匹配，命中列出短语与字段）；(8) 失败运行已在 §7 列出；(9) 每个 dirty 仓库在 `.md` 有标注行；(10) 关键指标有 source_ref；(11) 图表观察有 artifact ref；(12) `GOVERNANCE_INVARIANTS` 四句在渲染后的 `.md` 中逐字出现（缺任一句即失败）；(13) 渲染后的整份 `.md` 不匹配 `REPORT_SECRET_PATTERN`（失败时只指出所在节、不回显匹配内容）。(4)、(10)、(11) 在 M3 以"无指标、无图表"恒真并在结果中标注；不变式门禁的"无禁止用语"即第 (7) 项。不做 `tmp` 路径检查（工作区与运行目录可以位于 `$TMPDIR` 下，报告中的这类路径引用是合法事实）。任一失败：状态不变、返回逐项结果。通过：`status: reviewed`，按 D7 提交点顺序写 `.json` 后重渲染 `.md`。
- guard 的边界按 §5.2：只是枚举短语 lint，报告与文档不得把它说成合规充分条件；preset 指令里对 coordinator 写明。门禁措辞"措辞过四条不变式"的机器判据 = 第 (12) 项（四句逐字出现）与第 (7) 项（模型撰写节无禁止用语）；语义层面的合规不做机器检查，仍由 PI 审阅。

### D9 审批接线：`report_submit`、`report_decide` 与 PiGateDecision（Critical Path #3）

- report_submit(report_id) 前态 reviewed。policy-gate 在角色 deny 之后无条件 ask；reason 为固定前缀+report_id（落日志），displayReason 给摘要/路径（不落日志）。allowed-once 后工具先写 accepted 与 decision_history（approval_ref = 本次 exec.callId，comment null），再 TaskCard done、重渲染；其它 outcome 不执行、不改文件。O5 已通过真实 Web 卡证明：审批 id 仅在 asked/decided 事件，执行上下文只提供 callId。
- 拒绝后按候选(a)：coordinator 向 PI 索要非空 comment 与明确 rejected/revision_requested；不默认处置。report_decide 的二次卡回显两者，allowed-once 才记录 outcome、comment 与本次 exec.callId 并推进状态。两卡由日志中 report_id/callId 与审批 id 关联，模型可见即记录；不伪称 callId 本身是审批 id。
- 被拒 submit 卡的审计关联只经 session log：`approval/asked{toolName: "report_submit"}`（其 `reason` 携带该 `report_id`）之后紧随 `approval/decided{outcome ≠ allowed-once}`；同一 `report_id` 的 `report_decide` 卡 `reason` 也携带 `report_id`，两者由此在日志中关联。PiGateDecision 不记录被拒卡的引用。
- `accepted` 之后的 `report_decide` 拒绝（终态不可覆盖）；`archived` 无 M3 入口。
- 因此终态只在 `allowed-once` 分支写入；agent 无任何不经审批卡写终态的路径（grill Q12）。单用户工作台下 PI 自己用 bash 改文件不在保护范围（Non-Goal）。

备选 (b) 等 form seam（#420 否定）、(c) PI 专用工具无入口（K7）。

### D10 policy-gate 插件与 policy-gate-core 的去留（Critical Path #1）

- 插件挂全局行 `shud-policy-gate`（与 raw-guard 并列，不进 preset）。监听逻辑按固定顺序：先构造 `PolicyGateToolCall{ toolId, role, input, workDir }`（`spawnDepth`/`activeSubagentCount` 随 spawn 规则删除）调 `evaluatePolicyGate`，`deny` → `{kind: "deny", reason}`；求值器抛错 → fail-closed `deny`（受控 reason，不转发原始异常）；未被 deny 且工具为 `report_submit`/`report_decide` → `ask`（D9）；其余 → `next()`。角色 deny 先于报告工具 ask，因此 worker 调 `report_submit` 被直接拒绝，而不是弹卡问 PI。
- `role` = map(`readCallerPresetId(exec.agent)`) → coordinator/worker/unknown。唯一读取函数经公开 sessionProjections 服务读当前 agentPreset 投影；缺 Agent/会话/服务/有效值为 unknown。#425 的 header-only reader 在 #444 原地迁移，task_create 与 policy/restrict 共用，不另造读取路径；头部创建事实不能覆盖已切换身份。
- `DEFAULT_SHUD_POLICY_GATE_CONTEXT` 的三条 spawn 规则移除后，只加入 authority 规则 `role-tool-surface`：已知角色调用不在 `inherited ∪ local` 的工具即 deny（reason 仅角色/工具名），unknown 不适用。保留 id 恰为 raw-data-write、tool-parameter-schema-validation、role-tool-surface；前两者框架不新增实现。role-tool-map 是唯一两集合数据源：restrict 消费 inherited，执行门消费并集。模型可见性与执行授权分别验证。
- `policy-gate-core` 按规则族拆分为 `governance/policy-gate/{types,role-tool-surface,parameter-schema,evaluate}.ts`（每文件 ≤1000 行，测试同步拆）；删除 `spawn-depth-limit`/`spawn-concurrency-limit`/`spawn-profile-subset` 三条规则及其常量（dsh 原生 `maxDepth`、`maxActiveSubagents`、preset 子集语义取代——Canonicality），`RESERVED_AUTHORITY_POLICY_RULE_IDS` 中对应 id 一并移除并在 spec 写 Reason/Migration；删除 `isReservedAuthorityPolicyEvidenceId` 别名；`constraints.yaml` 的三条 baseline 与 `.large-file-guard.json` 排除项移除；knip `rules.duplicates` 转 error。
- 日志：每条 deny/ask 经 `ctx.logger("shud-policy-gate")` 一行（同 raw-guard 约定，#378 的可见性边界不变）。

- [O3 原 preset apply 与原 global-only allow 备选失败] → 已记录停止与 PI 重开；采用真实 Web 验证的 agent.ctx inherited allow，job_* 保留、local subagent 不传 restrict，角色执行面不变。
- [本次子代理 SHUD wake 未投递、原因未诊断] → 已实测 worker job_output/shud_collect 路径取得 succeeded RunRecord；prompt 必须等待收集再返回，coordinator 可兜底 collect。保留 M2 通知状态/预算，不因 M3 另造通知通道，不推广为所有子代理均不可唤醒。
